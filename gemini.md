# 🤱 Web Tracking ASI Ibu Menyusui (asiTrack) - Project Reference Guide

Welcome to the **Web Tracking ASI Ibu Menyusui (asiTrack)** project reference! This guide acts as the single source of truth for the codebase architecture, data schemas, complex logic definitions, and project implementation phases.

---

## 🎯 Project Overview & Objectives

- **Target User**: Postnatal mothers during their critical first week after childbirth (Days 1–7).
- **Core Purpose**: Monitor early lactation progress (breastfeeding tracking) to catch delayed lactogenesis, provide supportive education (articles + videos), and send daily push notification reminders.
- **Visual Aesthetic**: Premium, light theme with soft violet/purple accents (`#A78BFA`), rounded corners (`rounded-2xl`), smooth transitions, and high-quality UI/UX tailored for a warm, comforting maternal atmosphere.
- **Key Metric**: `hari_ke` (1 to 7) calculation based on the user's delivery date (`tgl_melahirkan`).

## 🗂️ Database Schema & Models (MongoDB)

All dates should ideally be stored in UTC but interpreted under **WIB (Asia/Jakarta)** for calendar logic.

### 1. `User` Model (`users` collection)
Tracks postnatal mothers, their profiling data, and notification tokens.
```typescript
{
  nama_lengkap: string;          // Required, Full Name
  username: string;              // Required, Unique, Lowercase, alphanumeric
  password: string;              // Hashed (bcryptjs)
  tgl_melahirkan: Date;          // Required, normalized to Start of Day in WIB
  
  // Optional profile details (can be edited/onboarded later)
  usia?: number;
  anak_ke_berapa?: number;
  alamat?: string;
  pendidikan?: 'SD' | 'SMP' | 'SMA' | 'D3' | 'S1' | 'S2' | 'S3';
  pekerjaan?: string;
  
  // Notification State
  fcm_token?: string | null;     // Saved FCM device token
  notif_enabled: boolean;        // Default: false
  profile_completed: boolean;    // Default: false
  
  created_at: Date;
  updated_at: Date;
}
```

### 2. `Admin` Model (`admins` collection)
Supports Role-Based Access Control (RBAC) for administration and content moderation.
```typescript
{
  username: string;              // Unique
  password: string;              // Hashed (bcryptjs)
  email: string;
  role: 'admin' | 'super_admin'; // Super admin can manage other admins
  created_at: Date;
```

Represents a questionnaire template.

### 4. `Response` Model (`responses` collection)
Stores daily answers given by users.

## ⚡ Core Business & Calculations Logic

### 1. `hari_ke` and WIB Timezone Calculations
Getting dates correct is crucial to avoid "missing days" or "future responses".
* **Normalizing to Start of Day (WIB)**: The delivery date (`tgl_melahirkan`) is stored normalized to the **start of day in WIB** (e.g. if birth occurs on `2026-05-21` at 10:00 AM WIB, we store it normalized as `2026-05-21T00:00:00+07:00`, which is `2026-05-20T17:00:00.000Z` in UTC).
* **Day Index Calculation**:
  - `hari_ke = 1` is the day **after** birth. E.g. if the baby is born on May 21 (WIB), then May 22 (WIB) is Day 1 of tracking.
  - Calculation:
    ```typescript
    import { utcToZonedTime } from 'date-fns-tz';
    import { differenceInDays, startOfDay } from 'date-fns';

    const TIMEZONE = 'Asia/Jakarta';
    const todayWIB = startOfDay(utcToZonedTime(new Date(), TIMEZONE));
    const birthWIB = startOfDay(utcToZonedTime(user.tgl_melahirkan, TIMEZONE));
    const currentHariKe = differenceInDays(todayWIB, birthWIB);
    ```
  - State boundaries:
    - `currentHariKe < 1`: Not started yet (user signed up prior to delivery).
    - `currentHariKe >= 1 && currentHariKe <= 7`: Tracking Period (Active).
    - `currentHariKe > 7`: Tracking Completed (Historical view only).

### 2. Form Auto-Fill & Milestones Logic
To decrease mother's burden, we use a smart milestone automation:
- The **Primary Question** (`is_primary: true`, default template: *"Apakah ASI sudah keluar?"*) is the milestone indicator.
- When the user submits `"ya"` for the Primary Question on any active day `hari_ke = N`:
  1. The app saves the responses for day `N`.
  2. The app **automatically backfills** response records for all remaining days up to day `7` (i.e. `hari_ke = N + 1` through `7`) with `"ya"` and `auto_filled: true` for the primary question.
  3. Once primary question is answered `"ya"`, the user's tracking is considered complete. No further daily forms are shown; instead, they see their successful completion dashboard.

### 3. Backfill Logic
Mothers may forget to fill out forms on a busy day.
- When opening `/form`, the API calculates all pending days in the range `[1, currentHariKe]` that have no responses.
- It displays separate cards for each missing day, allowing mothers to backfill their tracking out-of-order.

### 4. Push Notification Mock / Real Flow
Since Firebase credentials aren't active yet, the notification system is built with a decoupled interface:
- **Client Side**: Check if push notification permissions are allowed. If Firebase credentials are missing in `.env.local`, fall back to a beautiful **In-App Toast notification simulator** or a browser-native notification.
- **Server Side**: The Cron endpoint uses a decoupled notifier interface. If firebase configuration is missing, it logs sending actions to the console/system logs instead of crashing, allowing full dry runs of the cron logic.
- **Switching to Production**: To activate real push notifications, simply fill in the Firebase environmental variables in `.env.local` without needing to modify the main application code.

## 🔒 Authentication & Route Security (RBAC)

Two distinct authentication providers under NextAuth:
1. `user-credentials` -> Authenticates users using `username` and `password` check against `users` collection.
2. `admin-credentials` -> Authenticates administrators using `username` and `password` check against `admins` collection.

Sessions store standard properties plus `role: "user" | "admin" | "super_admin"`.

### Route Middleware Protection (`middleware.ts`):
- `/dashboard`, `/form/*`, `/profile`, `/pojok-baca/*`, `/video/*`, `/onboarding` -> require session role `"user"`
- `/admin/*` (except `/admin/login`) -> require session role `"admin"` or `"super_admin"`
- `/admin/admins` -> strictly require session role `"super_admin"`

## ⚠️ Important Implementation Guidelines

When writing code or modifications for this project, you **MUST** follow these rules:

1. **Strict WIB Calendar Logic**: Never use `new Date().getDate()` or `differenceInDays` without passing proper timezone offsets. Always calculate user days offset relative to Asia/Jakarta timezone.
2. **Mobile First UI Design**: Ensure all user paths (pages inside `(user)`) are strictly optimized for mobile displays. Wrap layouts in a `max-w-md` centralized frame to provide an elegant mobile app shell on desktops.
3. **No Placeholders**: Never use generic grey blocks or lorem ipsum for articles, videos, or cover images. Use our `generate_image` tool to create beautiful illustrations and populate database seed scripts with warm, helpful Indonesian language copy.
4. **Soft Violet Palette**: Adhere strictly to the color scheme. Do not introduce raw primaries like blue-600 or red-600. Use muted semantic equivalents (e.g. emerald-500, soft ambers, rose-500) and soft purple (`#A78BFA`, `#F5F3FF`) backgrounds.
5. **Session Safety**: NextAuth session tokens must include `id` and `role`. Route handlers and Server Actions must verify the actor's permission level matching the RBAC matrix.
6. **Resilient Mocking**: Do not let missing `.env.local` Firebase keys block user registration, profile saves, or dashboard navigation. Fail gracefully with log notifications and local fallbacks.
7. **Clean Database Seeds**: Ensure the seed script is fully idempotent. If re-run, it should safely update or bypass existing items rather than creating duplicates of templates or admin logins.

## 🛠️ Organic Project Implementation Roadmap

Rather than following a rigid day-by-day deadline, this roadmap is broken down by **functional milestones**. The user has total control over what is developed next, and we will present recommendations at the beginning of each phase.

### Phase 1: Core Foundation & Secure Shell
*   **Objective**: Scaffold a clean, robust workspace and implement authentication systems.
*   **Steps**:
    1. Initialize Next.js 15+ repository with TypeScript, Tailwind CSS, and standard directories.
    2. Configure Mongoose caching and declare all MongoDB models.
    3. Setup NextAuth.js v5 credentials handlers (users + admins) and create the `middleware.ts` route protection.
    4. Implement the seed script to preload the database (super admin, initial questions, and notifications).
*   **Developer Input**: *Completing this first is highly recommended, as it acts as the security backbone that all client/admin pages depend on.*

### Phase 2: Maternal Account & Onboarding Path
*   **Objective**: Allow mothers to securely sign up, configure their profile details, and go through the initial entry layout.
*   **Steps**:
    1. Build the welcoming Indonesian landing page (`/`).
    2. Implement Sign Up (`/auth/signup`) and Login (`/auth/login`) forms with robust Zod validation.
    3. Create the `/onboarding` page (which handles mock notifications activation).
    4. Create the mobile app viewport wrapper and the bottom navigation menu (`/profile`, `/dashboard`, etc).

### Phase 3: Daily Breastfeeding Tracking Engine
*   **Objective**: Build the core calendar tracking logic, daily questionnaire forms, and auto-fill mechanics.
*   **Steps**:
    1. Write the `/api/responses/state` API to precisely resolve the mother's `hari_ke` and find pending days in WIB.
    2. Implement `/form` UI which renders beautiful distinct cards for pending backfill days.
    3. Build the submission logic, including the confirmation modal and the smart milestone auto-fill mechanism.
    4. Construct `/form/history` allowing mothers to inspect active/completed/auto-filled badges.

### Phase 4: Maternal Education Center (Pojok Baca & Video)
*   **Objective**: Deliver educational rich-text articles and categorization filters for therapy/relaxation videos.
*   **Steps**:
    1. Implement backend collections and page routes for `/pojok-baca` (articles) and `/video` (short videos).
    2. Integrate robust video card layouts with automatic YouTube thumbnail generation and custom embedded players.

### Phase 5: Administrative Dashboard & CSV Export
*   **Objective**: Empower health practitioners and admins to moderate content, inspect active mother states, and filter/export data.
*   **Steps**:
    1. Admin portal login (`/admin/login`) and custom desktop sidebar layout.
    2. Real-time metrics overview chart (active users, response rates, milestone speed).
    3. CRUD management interfaces for Articles (using TipTap editor), Videos, Questions, and Notifications.
    4. Advanced filters for the mother registry (education levels, jobs, postnatal days) and full CSV download streams.

### Phase 6: Push Notification Cron & Live Deployment
*   **Objective**: Activate daily reminders and verify production readiness.
*   **Steps**:
    1. Wire up the server `/api/cron/send-notification` endpoint to match the morning, afternoon, and evening slots.
    2. Implement real Firebase Cloud Messaging integration fallback logic.
    3. Production verification: environment configurations check and Vercel hosting deployment.
